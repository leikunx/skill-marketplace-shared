## 理解核心模型

Multica 记录并协调工作。使用本地运行时时，已连接计算机上的守护进程领取队列中的执行任务，
并调用已安装的编码代理工具。服务端保存上下文、状态、执行过程记录、评论和上报结果。

| 对象 | 含义 |
| --- | --- |
| Issue | 持久化的工作目标、讨论、负责人和工作状态；一个议题可以经历多次执行。 |
| Agent | 配置好的代理身份、指令、技能、提供商/模型及运行时绑定。 |
| Run | 一次执行及其触发原因、状态、过程记录、结果和重试关联。 |
| Runtime / daemon | 工作区可使用的执行环境 / 发现工具、领取任务并回报结果的守护进程。 |
| Squad | 由领导代理负责路由与协调的团队对象；成员不会自动全部启动。 |
| Autopilot / issue wakeup | 新建周期性或事件触发的工作 / 继续处理已有议题。 |

常规流程为：**触发 → 入队 → 领取 → 准备环境 → 执行 → 回报 → 评审或继续推进议题**。
有关实现机制、分阶段委派、完成、重试和诊断，阅读[生命周期参考](references/lifecycle.zh-CN.md)。

## “完成”能证明什么

一次 run 标记为 `completed`，表示这次执行正常结束，不能据此认定议题目标已经实现。
需要检查结果、产物或 PR、验证证据，以及议题或工作流状态。
领导代理完成最初的委派回合，也不代表团队的父议题已经完成。

在内置议题流程中，代理将完成的工作交到 `in_review`；人工评审者或已配置的集成可以关闭议题。
自定义项目工作流可能提供不同的步骤约定。遵循当前执行携带的实际工作流上下文，
不要在所有场景下硬编码内置状态转换。

## 如何运用这些知识

讨论设计时，明确触发方式、执行机器、工作目录模式、委派机制及最终验收负责人。
与 Orca 比较时，Multica 的 **run 是一次执行**；Orca 的 **Run 是包含 Task 和 Dispatch 的协调命名空间**。

诊断时先收集只读证据：议题及执行记录、选定的运行时、正确 daemon profile 的状态和日志、
执行过程记录，以及源码产物。区分容量导致的排队、目录锁等待、工具缺失、运行时断连、
代理执行失败、结果投递失败，以及工作尚未通过验收。

操作前先查看当前的 `multica <command> --help`。
分配负责人、提及成员、发表评论和修改状态都可能触发代理；
仅加载本知识技能不会授权这些写入操作，也不会授权启用 Autopilot。

## 演进约定

任务内的执行结果记录在目标状态文件中，不写入本技能。改进提案与已验证的经验分开保存。
自主更新需要后续运行证明其客观改进，或确认稳定的安全、运行不变量。
在任务演进记录中记下触发原因、确切修改、证据、适用范围和回退条件；
在后续运行依赖修改后的指令之前完成验证。技能更新不会扩大授权范围。
