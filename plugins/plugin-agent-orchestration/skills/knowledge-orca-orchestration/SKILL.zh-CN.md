## 理解核心模型

Orca 围绕现有编码代理 CLI 提供开发环境和协调运行时。
协调代理拆解目标、启动工作代理；Orca 持久化任务归属、派发记录、消息、决策关卡及生命周期观测。

| 对象 | 含义 |
| --- | --- |
| Run | 持久化的协调命名空间和协调者收件箱；创建它不会自动调度工作代理。 |
| Task | 工作说明、依赖关系、结果和状态。 |
| Dispatch | 分配给工作代理的一次执行尝试；确定谁有权提交该 Task 的终态。 |
| Worker | 由协调者监督的代理会话，具有明确的执行位置和可观测生命周期。 |
| Message / gate | 用于沟通的消息，以及可以解除任务阻塞的显式决策。 |

常规流程为：**明确任务 → 启动相互独立的工作代理 → 结束当前回合并等待唤醒 → 接收消息
→ 确认各次尝试的终态 → 派发新就绪的任务 → 检查结果并汇报**。
Orca 当前指南要求协调者启动工作后结束当前回合；收到消息或生命周期事件时，由运行时唤醒协调者。

有关派发、依赖处理、完成语义、远程执行和恢复，阅读[生命周期参考](references/lifecycle.zh-CN.md)。
需要为结论提供依据或更新本研究基准时，阅读[来源索引](references/sources.zh-CN.md)。

## “完成”能证明什么

只有携带正确 Task 和 Dispatch ID、明确声明 `succeeded` 或 `failed`，且被接受的
`worker_done` 报告，才能确认这次分配的终态。没有输出、终端空闲、进程退出或一句普通的
“成功了”，都不能证明这一状态转换已经发生。
协调者仍需将产物和检查证据与 Task 的验收标准逐项对照。
Orca 的跟踪记录本身不能证明代码已完成集成、跨代理验证、合并或部署。

诊断时先确认尚未解决的是哪一层：启动就绪、工作代理存活状态、邮箱投递、
Task/Dispatch 终态确认，还是实际交付结果。选择恢复方法前，读取确切的操作回执和保留的输出。

## 如何运用这些知识

解释原理时，以一个具体任务为例，沿上述对象追踪完整流程，并引用对应参考资料。
与 Multica 比较时，注意 Orca 的 **Run 是协调命名空间**，而 Multica 的 **run 是一次执行记录**。
不能仅因两者名称相同就将其视为同一种对象。

执行已获授权的实际操作前，先读取与当前 Orca 版本匹配的 `orca-cli` 和 `orchestration` 指南。
按以下顺序确定可执行文件：优先使用 `ORCA_CLI_COMMAND`；处于带有 `ORCA_DEV_REPO_ROOT`
的开发会话时使用 `orca-dev`；在不由 Orca 管理的 Linux 终端中使用 `orca-ide`；其他情况使用 `orca`。
在无关的 Linux 环境中，直接运行 `orca` 可能启动屏幕阅读器。后续命令始终使用同一个已确定的可执行文件。

运行 `<resolved executable> skills get orchestration`，仅按当前操作需要读取其附加参考资料，
并以当前帮助输出核对参数。仅加载本知识技能不会启动工作代理、修改权限或创建调度任务。

## 演进约定

任务内的执行结果记录在目标状态文件中，不写入本技能。改进提案与已验证的经验分开保存。
自主更新需要后续运行证明其客观改进，或确认稳定的安全、运行不变量。
在任务演进记录中记下触发原因、确切修改、证据、适用范围和回退条件；
在后续运行依赖修改后的指令之前完成验证。技能更新不会扩大授权范围。
