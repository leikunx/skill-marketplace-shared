# Native Continuation and Scheduled Follow-ups

Read when later checks require recurrence or the user requests a pursuit window. For an away/asleep window, also follow [unattended handoff](unattended-handoff.md).

Consider scheduling during contract and handoff when checks must continue after the turn, such as review, build, reply, or deployment waits. Distinguish the outcome from its later-work trigger: a goal, skill, state file, or service-side auto-complete setting does not establish a Codex schedule.

If available, read `$plugin-shared:codex-scheduled-followups` for native continuation, same-chat scheduling and verification. This reference is optional; otherwise use the current [official scheduled tasks documentation](https://learn.chatgpt.com/docs/automations?surface=app) and guidance below. Discover actual schemas or supported app controls before scheduling; never invent tools, copy unverified parameters, or equate missing session tools with missing product capability.

- Default to native Goal automatic continuation in the current thread. Official [configuration guidance](https://learn.chatgpt.com/docs/config-file/config-reference) describes `features.goals` as persisted goals and automatic continuation, enabled by default. Use available goal tools or `/goal`, preserve the same thread and permissions, and leave the host scanner's interval at its default. Feature enablement and active goal status establish configuration; an observed automatic round establishes execution. Do not claim a documented fixed scan interval or an independently installed schedule.
- When the user needs a particular cadence or pursuit window, a supported native schedule attached to this same chat is the allowed scheduling option. Official [scheduled-task guidance](https://learn.chatgpt.com/docs/automations?surface=app) documents minute-based intervals. Discover actual controls/schema before using them; a product feature does not guarantee a callable tool in this session.
- Never start another Codex agent/session, fork the task, create a standalone scheduled chat, open an extra terminal, invoke `codex exec`/`codex exec resume`, or install Windows Task Scheduler, cron, launchd, or an external polling/queue wrapper for continuation. Missing native controls are a limitation to report, not permission to use that fallback. Do not edit runtime databases or queue self-prompts to simulate native recurrence. Preserve separately authorized validation rules.
- Reuse established execution scope and scheduling authorization. Specify cadence, timezone, stop condition or pursuit window, permitted actions, and notification destination; ask only for material missing choices. Editing or explaining guidance does not create a monitor; ordinary goals do not authorize indefinite recurrence.
- Check for a matching schedule before creating one. Record its identifier, enabled state, next run, exact definition, environment, shared state and requirements-ledger paths, bounded runtime, and non-overlap lease. Verify an actual scheduler-launched run with required tools, browser profile, authentication, and resulting evidence before claiming monitoring works; a saved definition or manual check is insufficient.
- If only external review or a confirmed running job remains, mark the current job waiting and preserve a separately authorized schedule until its stop condition. Keep goal, job, and scheduler status distinct. Follow the host's repeated-blocker policy; never fabricate progress, reset its audit, or imply that blocking a goal creates or cancels a schedule.
- On verified completion, perform any already-authorized notification once, then complete the native Goal or disable the native schedule as appropriate. At the configured end or user stop, stop new rounds and report the checkpoint. Distinguish active Goal configuration from observed automatic execution; without either a supported Goal continuation path or native schedule, future checks are not configured.

Use scheduler identifiers/next-run fields only for an actual native schedule. For native Goal continuation, record thread ID, goal status, last observed automatic round, and any unverified timing limitation. While the current turn is active, bounded waits may support an in-flight build check; they are not a persistent monitor. For away/asleep windows, also follow [unattended handoff](unattended-handoff.md).
